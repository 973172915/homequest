# 潍房智估 · AI 应用开发项目流程

> 数据基础：`data/sh_data.csv`，潍坊二手房挂牌数据，**18339 条 × 16 列**（已实测，见 `artifacts/reports/profile_report.txt`）。
> 本文档是施工图：每个阶段都写清「做什么 / 产出什么 / 怎么验收」。

---

## 一、先定三件事

| 问题 | 建议答案 |
|---|---|
| 给谁用 | 潍坊本地买房人（首置/改善）+ 想知道自家房子值多少的业主 |
| 解决什么 | ① 这套房值多少钱 ② 一句人话就能找到房 ③ 帮我对比、告诉我该不该出手 |
| 怎么算成功 | 估价 MAPE ≤ 8%；自然语言找房 Top10 命中率 ≥ 80%；接口 P95 < 3 秒 |

**明确不做**（写进 README，防止范围膨胀）：不做交易撮合、不做贷款审批、不做全国市场、不承诺投资回报。对外口径统一是「**挂牌价**参考区间」，不是成交价。

## 二、方向选型

| 方向 | 技术含量 | 难度 | 展示效果 |
|---|---|---|---|
| A. 智能估价（表格回归） | 机器学习 | 中 | 好，有数字有解释 |
| B. 自然语言找房（语义检索） | 向量检索 | 中 | 很好，演示直观 |
| C. 置业顾问（RAG + LLM） | 大模型应用 | 中高 | 最好，但易幻觉 |

**推荐：A + B 做主线，C 做增强。** 一个项目同时覆盖「传统 ML + 向量检索 + 大模型应用 + 服务化」，技术栈最完整。只做 C 像套壳，只做 A 缺少 AI 感。

### 3.1 规模与质量

| 样本量 | 18339 条 | 干净，无空字段、无非数值 |

| 整行重复 | 0 | 不需要整行去重 |
| 同一标题重复 | 434 条 | 近重复房源，需按「小区+面积+总价」判重 |
| id 范围 | 0 ~ 20825，缺 2487 个 | **这是抽样后的子集**，不是全市场 |
| 区县 | 8 个 | 潍城2736、高新2664、坊子2598、奎文2563、**寿光2520**、经开2155、寒亭1989、**青州1114** |
| 商圈 | 65 个 | 寿光/青州没有商圈粒度，`nearby` 与 `district` 同值 |
| 小区 | 1750 个 | 380 个小区只有 1 条房源 |
| 单价 | 中位 6837 元/㎡，P5–P95 4519–10892 | 最大 29346（豪宅），7 条 < 2000（疑似异常） |
| 面积 | 中位 109.4 ㎡，最大 542 ㎡ | 跨度大，需 log 化 |
| 楼层 | 全部可解析，总层数 1–34，中位 7 | 以多层老房为主 |
| 电梯 | 无电梯 10312（56%）/ 有 8027 | **电梯是大特征** |

### 3.2 五个决定性发现（直接决定建模方案）

**1）`unit_price` 是算出来的，不是独立信息。**
18339 条的「单价 vs 总价÷面积」偏差全部 < 1%，最大偏差只有 0.2%（4668 vs 4679）。
→ 所以「预测单价」和「预测总价」是同一件事，**不要做单价一致性清洗**（原计划里的这条可以删掉）。建模时取 `log(单价)` 做目标，输出时乘面积还原总价，一套模型两处用。

**2）数据是抽样的，不是全市场。**
id 不连续，缺 2487 个号，且 8 个区县里寿光、青州是县级市，房价与市区不可比。
→ 分区县评估指标，别只报一个总体 MAPE；文档里必须声明样本量。

**3）小区高基数且长尾重。**
1750 个小区，380 个只有 1 条房源。直接目标编码会剧烈过拟合。
→ 用**平滑目标编码**（向商圈均值收缩），并严格按小区分组切分 train/test，防止同小区房源同时进训练和测试。

**4）文本信息密度低。**
title 最长只有 35 字，中位 22 字，9939 条含多余空格，"学区"命中 0 次。
→ 别指望用纯文本模型撑起精度；文本更适合做检索（B/C 方向）和少量卖点特征（车位、储藏室、急售、满二/出税）。

**5）类别分布对建模友好。**
板楼 13760 / 板塔结合 3493 / 塔楼 1056 / 平房 30；精装 8056 / 简装 4373 / 毛坯 3046 / 其他 2864；商品房 18315 / 房改房 24。户型、楼层、梯户比 100% 可正则解析。
→ 清洗脚本不会卡在解析上，一天能跑通。

### 3.3 字段处理对照表

| 字段 | 处理动作 |
|---|---|
| `total_price` / `square` / `unit_price` | 数值化；目标取 `log(unit_price)`；`unit_price` 不单独做一致性清洗 |
| `size` | 正则 `(\d+)室(\d+)厅(\d+)厨(\d+)卫` → rooms/halls/baths |
| `floor` | 正则拆 `楼层档位` + `总层数`；派生「是否顶楼 / 是否底楼 / 楼层占比」 |
| `direction` | 11 种取值 → 多热编码 + `南北通透` 布尔（占 84%） |
| `elevatorNum` | 中文数字解析 → 梯数、户数、每梯户数（中位 2 户/梯） |
| `district` / `nearby` | 两级类别；商圈缺失时回退到区县 |
| `community` | 平滑目标编码 + 小区房源数 |
| `decoration` | 有序编码（毛坯 < 其他 < 简装 < 精装），"其他"占 15.6% 需单独看 |
| `type` / `elevator` / `ownership` | 低基数类别，直接 one-hot |
| `title` | 卖点关键词抽取（车位/储藏/急售/满二/出税）+ 检索用文本 |

## 五、开发流程（8 个阶段）

### 阶段 0 · 立项（0.5 天）
- 一页纸：用户画像、核心场景、成功指标、边界、里程碑。
- **产出**：`docs/立项书.md`
- **验收**：一句话说清「帮谁解决什么」。

### 阶段 1 · 数据体检 ✅（已完成）
- 已跑 `scripts/profile_data.py`，报告在 `artifacts/reports/profile_report.txt`。
- **结论**：数据干净可直接用，无缺失、无非数值、解析 100% 覆盖，主要风险是抽样、跨区县不可比、小区长尾。
- **剩余动作**：人工抽查 7 条单价 < 2000 和 1 条 542 ㎡ 的极端样本，确认是脏数据还是真实房源。

### 阶段 2 · 清洗与特征工程（2–3 天）
1. **近重复去重**：按 `(community, square, total_price)` 判重，处理 434 条同标题房源。
2. **解析**：`size`、`floor`、`direction`、`elevatorNum` 四列（见 3.3 表）。
3. **截尾而非删除**：单价按 P0.5–P99.5 截尾，保留 542 ㎡ 这类真实豪宅。
4. **派生特征**：面积段、楼层占比、是否顶/底、南北通透、每梯户数、小区房源数。
5. **防泄漏切分**：先按 `community` 分组切 train/test，再在训练集内算平滑目标编码。
6. **产出**：`artifacts/processed/clean.parquet` + `docs/特征说明.md`
- **验收**：清洗前后行数变化可解释（预计 18339 → 约 18300）。

### 阶段 3 · 估价模型（3–5 天）
1. **Baseline 先跑通**：「同商圈单价中位数 × 面积」，记录 MAPE，这是及格线。
2. **主模型**：LightGBM，目标 `log(unit_price)`，5 折 CV。
3. **分区县评估**：8 个区县各报 MAPE，寿光/青州单独看（分布不同）。
4. **SHAP 解释**：全局重要性 + 单套房「为什么是这个价」。
5. **残差分析**：找系统性高估/低估的小区，补特征或做残差修正。
6. **产出**：`artifacts/models/price_model.pkl` + `artifacts/reports/model_eval.md`
- **验收**：MAPE ≤ 8%（或比 baseline 低 30%）。

### 阶段 4 · 语义检索（2 天）
1. **拼检索文本**：`区县 + 商圈 + 小区 + 户型 + 楼层 + 装修 + 电梯 + 标题`
2. **向量化**：`BAAI/bge-small-zh-v1.5`（本地 CPU 可跑）
3. **建库**：FAISS，一条房源一个向量 + 元数据（价格/面积/区县，用于硬过滤）
4. **混合检索**：结构化过滤 → 向量 Top50 → 按「相似度 + 价格偏离」重排
5. **产出**：`artifacts/index/` + `scripts/build_index.py`
- **验收**：「奎文区 100 平以内 南北通透 精装 两居 预算 80 万」Top10 至少 8 条符合硬条件。

### 阶段 5 · LLM 应用层（3 天）
1. **意图解析**：自然语言 → 筛选 JSON（JSON mode），解析失败降级为关键词检索。
2. **RAG 生成**：只喂 Top-k 房源的必要字段，提示词强约束「只能引用给定房源，禁止编造价格/面积/小区」。
3. **固定输出结构**：推荐列表 + 对比表 + 每套优缺点 + 看房清单。
4. **评测集**：20–30 条真实问法，人工 1–5 分打「相关性/准确性/可读性」。
5. **产出**：`src/advisor/` + `docs/llm_eval.md`
- **验收**：幻觉率 < 5%；单次响应 < 8 秒。

### 阶段 6 · 服务化（2 天）
- FastAPI + Pydantic，三个接口：
  - `POST /estimate`：房源字段 → 单价、总价、价格区间、Top5 影响因素
  - `POST /search`：自然语言 → 筛选条件 + 房源列表
  - `POST /advice`：选中的房源 → 对比建议
- 模型启动加载一次；请求日志、超时、限流、CORS、`.env` 管密钥。
- **产出**：`app/api/main.py` + `/docs` 接口文档 + 冒烟测试。
- **验收**：三个接口 curl 通，错参数返回 422 而不是 500。

### 阶段 7 · 前端（3 天）
- MVP 用 Streamlit，三个页签：估价表单 → 价格卡片+区间+影响因素条形图；找房输入框 → 结果卡片；顾问勾选 → 对比报告。
- 生产版再换 Next.js。
- **产出**：`app/ui/streamlit_app.py`
- **验收**：非技术同事能独立走完「估价 → 找房 → 对比」。

### 阶段 8 · 评测、部署与迭代（2–3 天）
- 离线评测回归基线；Docker 打包；`docker compose up` 一键起。
- 监控：QPS、P95 延迟、错误率、估价分布漂移。
- 每月用新数据增量重训，模型存版本号可回滚。
- **产出**：`Dockerfile`、`docker-compose.yml`、`docs/运维手册.md`

## 九、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 挂牌价≠成交价 | 估价被质疑 | 口径写「挂牌价参考区间」 |
| 抽样数据、跨区县不可比 | 结论不严谨 | 分区县报指标；声明样本量 |
| 小区长尾（380 个仅 1 条） | 过拟合/泄漏 | 平滑目标编码 + 按小区分组切分 |
| 缺房龄/经纬度 | 精度天花板低 | 用总层数、电梯、楼型近似；接受 MAPE 8–12% |
| LLM 幻觉 | 假房源/假价格 | 只喂检索结果、结构化输出、答案带房源 id 可回溯 |
| 调用成本 | 上线贵 | 缓存 + 小模型分流 + Top-k 压缩字段 |
